# 2026-11-26 sweep

Four lanes ran on 2026-11-26 on the author's Linux host, each followed by a second agent told to refute
it. Every number below names its population; the probes are small and say so.

## 1. Do Claude Code and Codex pick skills on their own?

**Yes, both. They differ in how often.**

**What reaches the model.** No gap in either runtime.
- Claude Code 2.1.331: every hub-level Clade skill arrives with its full description. The 81 hub
  sub-skills (`ads-*`, `blog-*`, `seo-*`, `email-*`) are listed by name only, on purpose, through
  `skillOverrides`. No description is truncated. `check-skill-listing.py` reports 149 skills,
  36,784 characters against a 40,000 budget; the real listing, with plugin and built-in skills, ran
  to about 55,000 characters in the sessions read, and nothing was dropped.
- Codex 0.172.0: all 31 `clade:` plugin skills are listed in full. Codex's budget-overflow notice
  appeared in 0 of 297 sessions over 30 days.

**Known-answer probe.** 12 prompts aimed at Clade skills and 4 at each runtime's own built-ins, none
naming a skill. A throwaway 26-line Python repository, hooks disabled, one run per prompt, 40 headless
calls in all.

| | Clade skills | Built-in skills | Wrong picks |
|---|---|---|---|
| Codex 0.172.0 (`codex exec -s read-only`) | 12 of 12 | 3 of 4 | 0 |
| Claude Code 2.1.331 (`claude -p`, Opus 5.5) | 9 of 12 | 3 of 4 | 0 |

- Claude Code loaded nothing for `investigate`, `green`, `cso` and the built-in `code-review`, and
  nothing again on a second run of each. Given "run CI locally and fix what fails" it went straight to
  `ci-local.py` (2 of 2) where Codex loaded `clade:green`.
- Appending one sentence to the system prompt ("When a task matches a listed skill description, load
  that skill with the Skill tool before acting, even when the task looks small") flipped 3 of the 4.
  One run each, through `--append-system-prompt`, not through `CLAUDE.md`, and over-triggering was not
  measured.
- The tiny repository biases toward skipping heavyweight skills, so the misses are a floor for those
  skills, not a rate for real repositories.

**Real use, 30 days, the author's host, interactive sessions only.**
- Claude Code: 75 of 177 sessions had at least one model-chosen skill, 144 calls in all. 127 of the
  144 (88%) went to skills a global instruction file names. The owner typed no Clade skill as a slash
  command in those 177 sessions; the four `/radar` slashes were scheduled headless runs. Headless
  `claude -p` sessions made no model-chosen call in 259.
- Codex: about 150 of 212 TUI sessions had a model-chosen load (142 to 154 depending on how strictly a
  read counts as an installed-skill load).

**Why Codex picks more.** Not, on this evidence, its built-in "you must use that skill" rule: that
string is in the 0.172.0 binary but absent from the developer message of 5 of 5 `codex exec` rollouts
and 19 of 22 TUI rollouts on the host. What does track is naming: `green` and `delivery` are named in
`configs/CODEX_AGENTS.md` and fired in 56 and 96 Codex sessions; the Claude Code file names neither,
and they fired 0 times there. That correlation is not a controlled test.

**Candidates** (TODO.md): the sentence above, measured with negative prompts first; the probe
committed as an opt-in live eval; and `check-skill-listing.py` reading the real listing.
`regen-codex-plugin.py` wrote "Codex, Codex" into a runtime list and leaked `\"` into a
description; fixed in #PR:codex-desc.

## 2. The path-scoped rule channel on Claude Code 2.1.331

**Keep `configs/rules/` and keep `rule-injector.sh`.**

- On 2.1.331 (the author's host, every profile, 2026-11-24 17:35Z to 11-26 19:35Z) the hook delivered
  1,283 rules into 441 of 698 threads; the unit is one rule in one context segment of one thread. Rules
  that `configs/rules/` ships account for 575 of them.
- The native loader covered 6 of the 1,283 (0.5%), 5 of the 575. On 2.1.283 (2026-10-18 to 11-23)
  retiring the hook would have dropped 11,658 of 11,867 deliveries (98.2%).
- A probe of 14 `claude -p` sessions with every hook off, re-run in 7 more by the critic, shows what the
  native loader does not reach: a chain with a non-read segment (`cd X && cat f`), a pipe, several files
  in one command, Bash writes, and files outside the session's primary directory, where this
  repository's Workflow agents work in hand-made worktrees. A chain made only of reads does fire
  natively.
- The re-measure item's own step-1 command read 0 lines on this host, and its rule said zero means
  delete. Followed literally it would have deleted a working channel; the command is corrected.
- The "slash-less basename" reach the TODO credited to the hook also fires natively, on 2.1.283 too,
  so it was never a difference.

## 3. Gemini CLI: which bill it runs on

- On 2026-06-18 Google stopped serving Gemini CLI to free-tier and Google AI Pro/Ultra accounts and moved
  them to Antigravity CLI (`agy`), announced on the Google Developers Blog on 2026-05-19. Gemini CLI
  still serves paid Gemini API keys, Vertex AI, and existing Gemini Code Assist Standard/Enterprise
  customers; new Code Assist subscriptions are no longer sold.
- Google Workspace plans' bundled Gemini does not cover it: "These plans do not apply to the API usage
  which powers the Gemini CLI" (geminicli.com quota page, updated 2026-06-18). Workspace subscriptions
  do not include Antigravity plans either.
- So for an organisation Gemini CLI bills per token to a Google Cloud project, through an AI Studio key
  or Vertex AI. Google for Startups Cloud credits apply to that spend. A new AI Studio setup may be put
  on Prepay and need cash first; the Cloud welcome or free-trial credit cannot be used for the Gemini
  API.
- Headless pitfalls measured with Gemini CLI 0.70.0: in an untrusted folder headless mode exits 55
  (pass `--skip-trust` or `GEMINI_CLI_TRUST_WORKSPACE=true`, ideally from an empty temporary
  directory); user ADC under a Workspace re-authentication policy fails with `invalid_rapt`, so
  unattended runs need a service account. Reusing Gemini CLI's OAuth from another tool breaks Google's
  terms.
- For Clade: `second-opinion-gemini` cannot produce an answer as written (no binary on the host, a
  login path Google no longer serves, and exit 55 headless). A Gemini runtime adapter like Kimi's is not
  worth building: new features go to Antigravity CLI. Bulk offline Gemini work belongs on the Batch API,
  at half the interactive rate, not in an agent CLI.

## 4. Upstream, 2026-11-16 to 11-26

The 2026-11-23 radar run timed out with no digest, so this sweep covered the gap. 25 of its 30 claims
reproduced; four were corrected before anything here was written.

**Two Clade defects, found by probe.**
- `pre-tool-guardian.sh` failed open on a Bash command over 131,072 bytes (Linux `MAX_ARG_STRLEN`):
  every deny reason embedded the whole command in one `jq --arg`, jq could not start, and the hook
  exited 0 with no decision. `onFailure: "block"` does not catch an exit 0. 0 of about 432,000 Bash
  calls in the author's transcripts over 30 days exceeded the limit (largest 60,166 bytes), so it was
  latent. Fixed in #PR:guardian-large; the Python plugin guardian already denied at every size.
- `worker-checkpoint.sh` committed files that only the worktree's `.git/info/exclude` ignores: the
  shadow repository is fresh, so its own `info/exclude` was empty. A fresh worktree holds only tracked
  files, so the realistic leak is Claude Code's runtime files that this repository's exclude lists.
  Gemini CLI fixed the same shape in its own shadow repository (v0.68.0, pull 30034). Fixed here in
  #PR:checkpoint-exclude.
