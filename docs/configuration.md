### Orchestrator settings

After running `./install.sh`, a reference copy of every supported orchestrator
key lives at `~/.claude/orchestrator-settings.example.json`. To override a
default:

```bash
# Copy only the keys you want to change into the real settings file.
# Defaults from orchestrator/config.py:_SETTINGS_DEFAULTS apply for unset keys.
cat > ~/.claude/orchestrator-settings.json <<'EOF'
{
  "max_workers": 4,
  "auto_classify_retry": true
}
EOF
```

The `.example.json` is overwritten by every `./install.sh` run so it always
matches the current `_SETTINGS_DEFAULTS`; your real `orchestrator-settings.json`
is never touched. It is generated by `configs/scripts/regen-settings-example.py`
and a CI gate fails on drift — so "every supported key" is enforced, not just
asserted. Each key's meaning lives as a comment beside it in
`orchestrator/config.py:_SETTINGS_DEFAULTS`; JSON cannot carry those comments,
so read them there rather than guessing from the value.

## Control-plane authentication

Every orchestrator route requires a bearer token. This is not optional and not
a preference: `orchestrator/start.sh` binds `0.0.0.0` whenever it detects
Tailscale, so the server is offered to the whole tailnet by default, and every
mutating route here can open a session whose workers run with permissions
bypassed as the account that started the server.

The token is minted on first start and written to
`~/.claude/orchestrator-settings.json` under `api_token`, in a file the server
chmods to `0600`. The startup log prints the sign-in URL on the run that
created it:

```
Control-plane token minted. Open the UI with: http://<host>:<port>/web/?token=<value>
```

Open that URL once. The page stores the token, strips it from the address bar,
and sends it on every later request. To sign in from another device, append
`?token=<value>` to the UI URL there too, reading the value out of the settings
file.

For scripted access, send it as a header:

```bash
curl -H "Authorization: Bearer $(jq -r .api_token ~/.claude/orchestrator-settings.json)" \
  http://127.0.0.1:8765/api/status
```

Three deliberate exceptions:

| Path | Why it is exempt |
|------|------------------|
| `/`, `/web/*`, `/api/version` | The SPA shell and the stale-process probe. Neither reads nor mutates project state. |
| `/api/webhooks/github` | GitHub signs these with `webhook_secret`, and that path already fails closed on its own. |
| `/api/usage/ingest` | Remote `usage-agent.py` nodes authenticate with `usage_hub_token` — but only while `usage_ingest_token` is set. Leave it empty and the route falls back to requiring the control-plane token, closing the old "empty = open ingest" default. |

`GET /api/settings` masks every credential it returns, and a save that echoes a
mask back leaves the stored secret alone.

Setting `api_allow_unauthenticated` to `true` serves the control plane with no
authentication at all. It exists so the choice is explicit rather than implied
by an empty config; with no token and no opt-out, the server rejects.

## Standing multi-agent orchestration

By default Claude Code waits to be asked before it fans work out to agents. The
`Workflow` tool is explicitly opt-in, and a task that would obviously benefit
from parallelism does not on its own satisfy that opt-in.

One settings key changes that:

```bash
./install.sh --ultracode          # <15 agents per run
./install.sh --ultracode=large    # up to 50
./install.sh --ultracode=small    # under 5
```

which merges into `~/.claude/settings.json`:

```json
{ "ultracode": true, "workflowSizeGuideline": "large" }
```

With it on, Claude plans a workflow for each substantive task instead of waiting
for you to type `ultracode` in the prompt. It also raises reasoning effort to
xhigh, so **it spends materially more per turn** — that is the right trade when
you are driving a fleet from the terminal and the wrong one if you installed
Clade for its commit hook. Off by default for that reason.

Turn it off with `jq 'del(.ultracode)' ~/.claude/settings.json | sponge` or by
editing the file.

Two related environment keys, both in the `env` block of the same file:

| key | default | what it does |
|-----|---------|--------------|
| `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` | 10 | how many read-only tools and subagents run at once |
| `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` | 3, set to **1** by `install.sh` | layers of nesting below the main loop |

The depth cap is deliberate — it enforces "subagents must not delegate
recursively" — and it costs a workflow nothing, because a Workflow script
orchestrates from the lead rather than by nesting.

**Check whether a run used its parallelism**, rather than assuming:

```bash
python3 configs/scripts/workflow-scorecard.py --since 7
python3 configs/scripts/workflow-scorecard.py --since 0 --ledger   # keep one row per finished run
python3 configs/scripts/workflow-scorecard.py --ledger-summary     # the figures, from the ledger
python3 configs/scripts/workflow-scorecard.py --outcome            # owner messages after each run, to label
```

An `outlived` share of 15% or more means the shape was wrong: a barrier where a
pipeline would do, or units too coarse. A high `serial` share is a one-agent
stage instead, which only a shorter stage fixes. Over 285 parallel runs on the
author's two profiles (4,038 agents, 394 h, started 2026-09-22 → 10-24 UTC),
16.9% of makespan was an agent outliving its siblings and 35.5% was one-agent
stages: `--ledger-summary --recorded-before 2026-10-24T03:34Z` over the
author's ledger.

Claude Code deletes transcripts after 30 days, and a figure derived from them
goes too. `--ledger [PATH]` appends one row per finished run to
`$CLAUDE_CONFIG_DIR/workflow-scorecard/runs.jsonl` (`~/.claude/…` when the
variable is unset or empty), and the scan reads that config dir's own
`projects/` too. It is append-only, counted per API call, and writes nothing
for a run still in flight. A row records one end of a run: a run resumed under
its run id that ends again gets a second row, and a reader takes the last one
per run id. Run it under one profile: every profile's runs land in every
profile's ledger. `--ledger-summary [PATH]` reads that back into the figures
above; `--recorded-before WHEN` keeps only the rows a statement was made from.
`--outcome` prints, per end of each finished run, what the owner typed in its
lead session in the 6 hours after it, as JSONL with `label: null` for weekly
labelling by hand.

**Check whether the merged work stuck**, not only how much ran. The scorecards
above measure inputs, and volume does not track value: Faros AI's 2025 study of
10k+ developers saw +98% PRs merged and +91% review time with no company-level
gain, and the AIDev dataset of 456k agent-authored PRs found them accepted less
often than human PRs (both as cited by the brief for this script, not
re-verified here).

```bash
python3 configs/scripts/outcome-scorecard.py --since 14 --tokens   # every repo you merged into
python3 configs/scripts/outcome-scorecard.py --repo OWNER/NAME --json
```

Each PR the author merged in the window is **reverted** (a later commit or PR
reverts it by sha, exact `Revert "<title>"`, or a revert PR naming `#N`, at any
time up to now), **fixed-forward** (a later `fix:`/`hotfix`/`bugfix` PR by
anyone into the same base branch, within `--settle` days, shares a changed path
other than TODO.md, PROGRESS.md, CHANGELOG\*.md, a `changelog/` directory,
README\*.md, docs/facts.json or a lockfile), **settling** (younger than
`--settle`, default 7 days, and never counted as kept) or **kept**. `--settle`
bounds only the fix-forward search and the settled/kept split; a revert counts
whenever it landed. The author's own PRs that revert another PR are listed as
**revert** and not rated, by the same title rules, whether or not that PR was
read: a revert of a PR merged before the window says "target outside the
window". Undoing a change is not new work that stuck. The same base branch,
because a repository that lands each change on `dev` and again on `main` would
otherwise read the second landing as a fix of the first; PRs into a non-default
base are still scored, and each repository's block says how many there were.
The kept rate is over PRs
at least `--settle` days old, so `--since 7` prints none (young PRs are still
listed as reverted or fixed-forward); use `--since 14`.

Fixed-forward is a signal whose precision has not been measured, and bad work
that nobody touched again reads as kept. Each block prints how many
fix-forwards shared a path that is not Markdown, and the paths they most often
shared. Across the author's host (`--since 14` to 2026-11-06: 17 repositories,
715 PRs by the author) it flagged 369, 247 of them through a non-Markdown path,
and the most shared paths were a package version file (34), a per-app
VERIFY.md checklist (23) and system and model docs — shared state that no path
rule can tell from a repair. On this repository the shared paths are mostly
context docs: over the same window, 15 of 33 PRs were fixed-forward and 6 of
those shared only Markdown (CLAUDE.md, configs/CLAUDE.md, docs/how-it-works.md,
which nearly every PR here edits); docs/how-it-works.md was the most shared
path (×4). So read the fixed-forward count as inflated until a labelled sample
measures it. Each block also reports the fan-in, every fix credited as the
fix-forward of 3 or more PRs (`fan-in: #N fixed-forward K PRs`); a high fan-in
usually means the fix touched a file those PRs share, such as an append-only
log or manifest, not that it made K repairs.

Review load is open-to-merge time (median, p90), the share merged with no
review from anyone but the author, and median lines changed. `--tokens` divides
this host's Claude Code transcript tokens by merged PRs; per settled and per
kept PR it divides only the tokens spent up to now − `--settle`, when those PRs
merged, because the last `--settle` days' tokens produced only PRs too young to
settle. Those tokens are host-wide, not attributed per PR, and Codex and Kimi
usage is not counted, so with `--repo` every per-PR figure overstates that
repository set's cost, which the report says. When `gh pr list` times out with a
gateway error (HTTP 502/503/504, which large monorepos hit because GraphQL
computes every PR's files), the script re-reads the repository through a
paginated GraphQL search at 10 PRs per page and notes it; any other repository
gh cannot read is named as not measured, never counted as zero. `/retro` runs
this as its Outcomes step.

**Roll up what merged PRs could not verify.** Every PR body that `/create-pr`,
`/delivery` and `/ship` write, and this repository's PR template, carries two
fixed lines:

```text
Review depth: none | skimmed | read-in-full
Could not verify: none | <item>; <item>
```

`Review depth` is how far someone other than the author read the diff, with an
optional `(by …)`. `Could not verify` lists what was not checked, each item a few
words naming the surface, with its reason in parentheses. One unverified item is
a caveat; the same item in PR after PR is a missing capability.

```bash
python3 configs/scripts/pr-verification-gaps.py --since 14         # the repository gh resolves here
python3 configs/scripts/pr-verification-gaps.py --repo OWNER/NAME --json
```

It reads every PR merged into one repository in the window, by any author, and
groups the items by their words (case, emphasis, trailing punctuation and a
trailing `(reason)` are ignored). The top `--top` (default 3) items that recur in
2 or more PRs are printed as candidate `- [ ]` TODO entries; nothing is written.
Lines inside an HTML comment or fenced code, or opening in inline code, are not
read; a `<placeholder>` or the `a | b` format line counts as unfilled; and a PR
without the line is not counted as verified: when no PR states it, the section
says NOT MEASURED. Both lines are self-reported, so review depth is checked
against the forge, and a claimed reading that no submitted review by anyone but
the author backs is listed as a question, since a reader outside GitHub leaves
no review there. On this repository's 35 PRs merged in the 14 days to
2026-11-06, neither line appeared yet. `/retro` runs this as its Step 2c.

## Context window policy

**Opt-in, and not yet shown to cost nothing in quality.** One settings key makes
Claude Code compact a 1M-context session at about 317K tokens instead of 967K:

```bash
./install.sh --context-policy        # write it (only where you have not set your own)
./install.sh --no-context-policy     # remove it (only if Clade wrote it)
CLADE_CONTEXT_POLICY=on|off ./install.sh   # the same, for scripted installs
python3 ~/.claude/scripts/context-policy.py status   # who owns it, what shadows it
```

**What is written.** A top-level integer in `~/.claude/settings.json`:

```json
{ "autoCompactWindow": 350000 }
```

Compaction fires at the window minus `min(maxOut, 20000)` minus 13,000, so
350,000 − 33,000 = 317,000 on Opus 5.5 (formula read in the 2.1.283 and
2.1.318 binaries). Claude Code caps the value at the model's own window, so it
is a no-op on 200K models. Clade never writes `CLAUDE_CODE_AUTO_COMPACT_WINDOW`,
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, `modelSettings`, managed settings or a
`--autocompact` wrapper, and never sets or clears `DISABLE_AUTOUPDATER`.

**It reaches new sessions only.** Claude Code 2.1.283 reads `autoCompactWindow`
once, when a session starts, and keeps it in the session's state; a later write
to settings.json does not reach a session that is already running (read in the
2.1.283 binary, and observed on the author's host: after the write, a running
session reached 379K and a running workflow subagent 414K without compacting).
`/autocompact` is the one path that updates a live session, so in a session that
predates the install either run `/autocompact 350k` — it writes the same
350000, so Clade still owns the value — or restart it with `claude --continue`.
Subagents take the window of the session that launched them.

**Why 350000.** A replay of 30 days of transcripts on the author's host, to
2026-11-05, both profiles — 224 main and 5,891 subagent threads, 82.0B tokens,
$32.2K at list price — with behaviour held fixed:

| Window | Saving at list price | Compactions |
|---|---|---|
| 300K | $3,885 (12.1%) | 2,416 |
| **350K** | **$3,734 (11.6%)** | **1,371** |
| 400K | $3,304 (10.3%) | 827 |

350K keeps 96% of the 300K saving with 43% fewer compactions, and it is the
robust pick across the five simulation variants: it saves at least $2,732 in
every one, with a maximum regret of $545 (300K: at least $2,062, regret $670).
Fewer compactions matter because each one costs something: the 23 real
compactions in that window (all near 967K) were followed by +2.10 pp tool errors
over 30 turns [+0.49, +4.02].
On quota, a fitted weight for a cache read of about 0.028× an uncached input
token (95% CI 0.022–0.036) puts the main-thread quota saved at 37.4% for 300K and
33.1% for 400K, against 30.3% for 200K; 350K itself was not simulated under that
weight. The full record is the `measurement` block of
[`configs/context-policy.json`](../configs/context-policy.json).

Confidence: **cost MEDIUM-HIGH, quota MEDIUM, quality LOW-MEDIUM.** No session
in the data ever compacted near 317K, so "no performance loss" rests on indirect
evidence. That is why it is opt-in: the trial and its rollback thresholds are in
[TODO.md](../TODO.md#2026-11-05-context-policy-follow-ups), and the default
flips only after it passes.

**Subagents share the value.** On 2.1.283 a subagent inherits the main window,
and no setting separates them, so this one value serves both. The simulation
saves subagents $1,873 (6.9%) at 350K, with 1,130 compactions in 934 of 5,891
agents, and turns against them lower down: at 200K they cost 16.9% more quota
under the fitted weight. Do not lower it below 300K while they share it.

**Your value always wins.** Clade records what it wrote in
`~/.claude/.clade-context-state.json` and changes or removes the key only while
settings.json still holds exactly that value:

- a value you set (by hand or `/autocompact N`) is yours: never rewritten, and
  `--no-context-policy` leaves it alone. Clade records that it is yours, so
  deleting it later does not hand the slot back;
- a key you delete (or `/autocompact auto` on 2.1.283), whether Clade wrote it
  or you did, is recorded and never re-added, until you run
  `./install.sh --context-policy` again;
- your on/off choice persists, because `fleet-install.sh` runs `./install.sh`
  with no arguments;
- `./uninstall.sh` retracts the value the same way `--no-context-policy` does
  and removes the record. If the Claude Code version cannot be read it removes
  nothing and keeps the record, the only proof that the value is Clade's.

**Precedence, by Claude Code version.**

- **2.1.283 (installed on aries):** `/autocompact N` overwrites this same key and
  `/autocompact auto` deletes it, so the ownership check above is what protects
  your choice. `modelSettings[model].autoCompactWindow` is ignored.
- **2.1.288 and later** (2.1.318 read from the binary, not run): the top-level key
  becomes the cross-model default. A per-model `/autocompact` value wins over it,
  and `/autocompact auto` writes a per-model `auto` that falls back to the 967K
  default without touching Clade's key.
- The env var and managed settings outrank it, and so does a per-launch
  `--autocompact` flag (read in 2.1.318); from 2.1.296 subagent frontmatter can
  lower it further.
- **On both versions it outranks a window Anthropic sets for your account
  server-side, so Clade steps aside for one.** The 2.1.283 binary's window
  resolver checks the env var, then this settings key, then the `clientdata`
  tier, then the experiment tier. Claude Code caches the `clientdata` window in
  its global config, per model, as `autoCompactWindowsCache` or as
  `rowan_thicket` in the client-data cache (`clientDataCacheSlots.<slot>.data`,
  or the legacy `clientDataCache`). While either is a non-empty object, Clade
  removes a value it wrote and writes none (a value you set is left alone), and
  `status` lists the cache under "shadowed by" and prints no compaction point.
  Once the cache is null or empty again, the next install writes the value back.
  The files read are `~/.claude.json` (beside `~/.claude`),
  `$CLAUDE_CONFIG_DIR/.claude.json`, and the legacy `.config.json` in the config
  directory, which 2.1.283 reads first when it exists; one that is absent,
  unreadable or invalid is no signal. This is **best-effort**: the cache names
  are undocumented and were read from the 2.1.283 binary, so a later version
  that renames them goes unseen, and the experiment tier is not detected at all.
  The fallback is the version check: on a Claude Code newer than the verified
  one, `status` prints a NOTICE to re-verify, a follow-up in
  [TODO.md](../TODO.md#2026-11-05-context-policy-follow-ups).

**It steps aside** — writes nothing — when any more specific mechanism is
present: `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`,
`DISABLE_COMPACT` or `DISABLE_AUTO_COMPACT` (in settings `env` or the install
environment), `autoCompactEnabled: false`, any `modelSettings.*.autoCompactWindow`,
or managed settings that set `autoCompactWindow` or any of these. Managed
settings means `managed-settings.json` and the `managed-settings.d/*.json`
drop-ins beside it (dot-files skipped, as Claude Code skips them), and a
managed file, or a `managed-settings.d` directory, that exists but cannot be
read counts as setting all of them. It also writes nothing while a server-side
window is cached (above).

**It fails closed.** `claude` is looked up on PATH, then in `~/.local/bin` and
`~/.claude/local` by path, because `fleet-install.sh` runs `./install.sh` over a
non-interactive SSH shell that never sources the rc file adding `~/.local/bin`
to PATH. The version comes from every line of `claude --version` (stdin closed,
10 s timeout), else from a `.../versions/X.Y.Z` install path. Unknown, or below
2.1.236, means nothing is written and nothing is removed. A version newer than `verified_through_cc_version` (2.1.283) still
gets the value, which is documented and schema-checked, plus a notice to
re-verify. `status` prints the same comparison and names
`https://code.claude.com/docs/en/model-config` as the page to re-check; nothing
here touches the network. It prints a compaction point only when nothing
shadows the key, and for a value outside 100,000–1,000,000 (which Claude Code
drops) it prints the default point, not one computed from the dropped value. A maintainer withdraws the value fleet-wide by setting
`retire_from_cc_version`: the next install at or above that version removes the
Clade-owned value and only that.

**Codex and Kimi: report-only.** `status` reads a few non-secret keys of
`~/.codex/config.toml` and `~/.kimi-code/config.toml`, prints where each
compacts, and writes nothing to either.

- **Codex** (derived on codex 0.166.0): gpt-6-astra already compacts at 244,800,
  90% of its 272,000 window. No change.
- **Kimi** (derived on kimi 2.2.0): k3 compacts at 891,290 (0.85 × 1,048,576).
  Deferred while Kimi is idle. The manual option, if you want it, is a per-model
  override that survives a model refresh:

  ```toml
  [models."kimi-code/k3".overrides]
  max_input_size = 350000   # compacts at 297,500; also applies to k3 subagents (not simulated)
  ```

  Never use the global `compaction_trigger_ratio` or `reserved_context_size`:
  they hit every model, and the ratio's floor of 0.5 cannot reach 350K.

## Add a correction rule manually

Edit `~/.claude/corrections/rules.md`:
```
- [2026-02-17] imports: Use @/ path aliases instead of relative paths
- [2026-02-17] naming: Use camelCase for TypeScript variables, not snake_case
```

## Conversation-mode projects

Some repositories are conversations rather than codebases: a personal
assistant's persona, a journal, a coaching log. The hooks are tuned for
engineering work, and in such a repository they made the assistant run a chat
like a build. Declare it with an empty marker file:

```bash
touch .claude/conversation-mode
```

What changes, and only in that repository:

- **Corrections** (`correction-detector.sh`): the notice asks for a one-line fix
  in the reply instead of a rule, records a lesson only if the mistake repeats
  or had real consequences, and points at wherever the project's own CLAUDE.md
  keeps lessons, never `.claude/corrections/rules.md`. The prompt is still
  counted in the local `history.jsonl` but is not written to
  `cross-project-rules.jsonl`, which lives in the sync store and its remote.
- **Session start** (`session-context.sh`): the git state, handoffs, the
  project's own rules and the language rule stay; the host fingerprint,
  containers, other projects' correction rules, the model guide, "close the
  loop", skill routing, kit and revert warnings go; and the project's rules are
  no longer auto-promoted into its CLAUDE.md.
- **Not changed**: the Stop completeness check is a prompt hook and cannot read
  the marker. It treats waiting on the user as a correct stop, which is what a
  conversation turn usually is.

### Private stays on this machine

The dotfiles sync store is a git repository with its own remote, and
`sync-push.sh` stages everything in it. Before this guard, one machine pushed 87
previews of a personal conversation to GitHub. Three pieces now keep private
content local, whichever writer slips:

- **The exit check.** `sync-push.sh` reads `~/.claude/private-projects` (absolute
  project paths) and `~/.claude/private-keywords` (literal strings), one per
  line, both outside the store so they never sync themselves. A staged line
  containing any of them is removed from an append-only `*.jsonl` log; any other
  file carrying one is withheld from the commit, left in place, and named in
  `~/.claude/.sync-conflicts.log`.
- **Registration.** Session start adds every conversation-mode project to
  `~/.claude/private-projects` (both the given and the physical path).
- **Project memory.** `sync-link-projects.sh` (run at session start) moves each
  project's auto-memory directory into the store so it has git history. It
  covers `~/.claude/projects`, `$CLAUDE_CONFIG_DIR/projects` and every
  `~/.claude-profiles/*/projects`. A project listed in
  `~/.claude/private-projects`, or carrying `.claude/conversation-mode`, is
  never moved or linked: its memory stays a local directory, and a link it
  already had into the store is replaced by a local copy. A memory directory
  whose store copy holds a different version of a file is left in place and
  listed in `~/.claude/.sync-memory-conflicts`, which `sync-health.sh` prints at
  the start of every session until you merge it by hand (the history is in
  `~/.claude/.sync-conflicts.log`). The session-start hook times out at 30 s,
  so the linker starts no new directory after `CLADE_SYNC_LINK_BUDGET` seconds
  (default 10) and the next session resumes; to move a long backlog at once,
  run `CLADE_SYNC_LINK_BUDGET=0 bash ~/.claude/scripts/sync-link-projects.sh`.
  `sync-link-projects.sh --dry-run` lists what would move.
- **Private sessions.** A personal-mode skill can mark a session wherever it was
  started: `touch ~/.claude/private-sessions/$CLAUDE_CODE_SESSION_ID`. The
  correction hook then treats it like a conversation-mode project.

Keep keywords specific — a word that also appears in ordinary work files will
hold those files back too, and the log is where that shows up.

Measured on the repository this was written for: 103 rules, 90,172 characters,
had been promoted into the CLAUDE.md loaded by every chat, and 13 of them
recorded that an earlier rule had not prevented the same mistake.

## Adjust quality gate thresholds

Edit `~/.claude/corrections/stats.json`:
```json
{
  "frontend": 18,
  "devops": 30,
  "backend": 12,
  "ml": 4,
  "ios": 0,
  "android": 0,
  "systems": 0,
  "academic": 0,
  "schema": 0,
  "unknown": 554
}
```

A domain with at least 3 corrections **and** at least half the worst real domain's count triggers strict mode (adds build + test checks); everything else runs the standard checks. These are counts, not rates — nothing records a denominator — so the comparison is between domains. `unknown` is the unclassified bucket and is excluded from both sides. Domains, matching `_STATS_SEED` in `correction-detector.sh`: `frontend`, `backend`, `cli` (shell), `mobile` (Dart/Flutter), `ml`, `devops`, `security`, `ios`, `android`, `systems` (Rust/Go), `academic` (LaTeX), `schema`. `cli` is the one a shell-heavy repository like this one resolves to most often.

## Enable end-to-end browser verification

`/verify` ships a **UI Interaction** strategy that drives a real browser (navigate
the running app, snapshot pages, click/fill, flag console errors and broken flows)
— the only verification that proves a frontend change actually works rather than
just compiles. It runs only when the Playwright MCP is wired in. Enable it per
project:

```bash
configs/scripts/setup-browser-verify.sh /path/to/project       # merge config + install Chromium
configs/scripts/setup-browser-verify.sh /path/to/project --remove   # disable
```

This merges the Microsoft Playwright MCP (`@playwright/mcp`) into the project's
`.claude/mcp.json` — the file both orchestrator worker spawns (`worker.py`) and
`/verify` (`start.sh`) already load via `--mcp-config` — and installs the Chromium
binary. Existing MCP servers in the file are preserved. Requires Node (`npx`),
which Claude Code already provides.

Once enabled: `fix`/`test` worker tasks can reach the browser tools (allow-listed
as `mcp__playwright` in `config.py:_TOOL_SUBSETS`), and `/verify` emits
`INTERACTION_RESULT: pass|partial|fail` plus `[BUG]`/`[UX]` findings to
`.claude/playwright-issues.md`, which the loop consumes. Cost note: every worker
on that project then launches a Playwright MCP subprocess — run `--remove` for
projects with no frontend.

**Troubleshooting** (seen live on a real Next.js project):
- The Chromium install may print a Playwright version-mismatch box and `Removing
  unused browser at …chromium-NNNN` — this is normal: `npx playwright install`
  resolves a different Playwright version than `@playwright/mcp` bundles, so it
  swaps the browser build. The setup still succeeds; verify with
  `ls ~/.cache/ms-playwright/` (a `chromium-*` dir present = good).
- The `/verify` browser step (and the worker visual-verify directive) only fires
  when the project is detected as a frontend — detection reads the project's
  `package.json` for a frontend framework (`next`/`react`/`vue`/`svelte`/…) **or**
  a `## Project Type` / `Frontend:` line in CLAUDE.md. A frontend project whose
  CLAUDE.md only describes the stack in prose is still detected via package.json.

## Mutation testing (patrol lane)

Coverage shows a line *ran* during tests; mutation testing shows a test would
*catch a bug*. Enable the lane to surface hollow tests (code that's executed but
never asserted — the real risk for agent-written tests):

```jsonc
// ~/.claude/orchestrator-settings.json
{
  "mutation_scan": true,
  "mutation_targets": ["orchestrator/worker_review.py", "orchestrator/error_classifier.py"]
}
```

Requires `mutmut` (`pip install mutmut`); absent → the lane logs a hint and
no-ops. `mutation_targets` (project-relative paths) is **required** — mutation
targets are project-specific, so with none configured the lane no-ops. It runs
every ~6h (mutmut runs the whole suite once per mutant, so it is the most
expensive lane — never a commit gate); pick a few high-signal modules where a
silently hollow test is most dangerous. **Ratchet:** the first run seeds a survivor baseline at
`.claude/mutation-baseline.json` and creates **no** tasks; later runs create a
`test`-type task only for *newly*-surviving mutants (a regression in test quality),
capped at 10/run. Killed mutants drop from the baseline automatically.

## Add a new hook

1. Create `configs/hooks/your-hook.sh`. Within its first 10 lines it must carry
   exactly one provenance line, with ` · retire-when: ` (a middle dot) between
   the two halves:

   ```bash
   # exists-for: <incident or need>, <YYYY-MM-DD>, <commit sha or #PR> · retire-when: <condition>
   ```

   - **exists-for** names the recorded incident the hook answers, its date and
     the commit or PR that records it. If nothing records one, write
     `no incident recorded (added <date> in <sha or #PR>)` and the need it
     serves; never invent an incident. A cited sha must resolve to a commit; a
     new hook may cite its own open PR.
   - **retire-when** names the condition under which the hook may be removed.
     A hook that blocks retires only after an ablation shows no harm without
     it, because a guard that never fires may be working. For any hook, a
     condition resting on it going quiet ("unused for 60 days", "has not
     fired", "0 hits", "last fired 90 days ago") is refused unless it names an
     ablation. The check matches these wordings, not the meaning, so state the
     condition plainly rather than around it.
   - `/generate-hook` emits this line for you to fill. A `<…>` or `{…}`
     placeholder left in it is refused.
2. Add the hook definition to `configs/settings-hooks.json`
3. Run `bash tests/test-hook-provenance.sh`: it checks the line on every hook,
   and that every hook the settings wire is among those checked
4. Run `./install.sh`
